Know the sampling limits

Hardware and FPS / latency CSV values are periodic summaries, so use them for sustained load and broad relationships. A matching FrameTime file adds individual frame durations and makes hitch timing much more representative, but hardware readings remain sampled and should not be treated as proof of the exact cause of one frame spike.

Select the ? above the chart for navigation and keyboard controls.

Remember: lower frame time is better; CSV metrics show sampled trends rather than every frame; zooming recalculates the statistics; and matching changes are clues, not proof of cause.
Reading the chart and tooltip
  • Current row follows the row under the pointer and steps between measurements actually recorded in a CSV.
  • All displayed rows compares only rows currently visible in the scrolling chart.
  • The nearest sample time is shown once per CSV file because different files may record at slightly different moments.
  • FrameTime points are individual frames. When one CSV sample is visible after a tight zoom, a dashed line holds that recorded value and a dot marks its timestamp.
  • On the FPS row, the solid line is AMD’s logged FPS. When FrameTime is also loaded, the dashed line is FPS recalculated from raw frames over the preceding one second.
Choosing a diagnostic view
  • CPU ↔ GPU helps identify whether an FPS change occurs while CPU or GPU load is high. Total CPU usage can hide a limit on one or two cores.
  • GPU limits compares FPS with GPU load, clock, power, and hotspot temperature.
  • GPU HW shows all numeric GPU hardware metrics.
  • CPU HW shows all numeric CPU metrics plus system memory. It can be combined with GPU HW.
  • Frame pacing places raw FrameTime beside sampled FPS and stutter indicators.
  • Frame time only gives individual frame durations the most space. Large spikes use an expanded upper scale.

These views help you find relationships worth investigating. They cannot prove that one metric caused a problem.

Understanding the statistics

Statistics use the visible time period and the cards at the top follow the rows currently visible on screen.

  • CSV metrics show Minimum, Average, and Maximum from their logged samples.
  • FrameTime shows Average, P99, P99.9, Worst, and average FPS calculated from individual frames.
  • 1% Low FPS is calculated as 1000 divided by P99 frame time. It needs at least 100 visible frames.
  • 0.1% Low FPS is calculated as 1000 divided by P99.9 frame time. It needs at least 1,000 visible frames.

The lows belong to the raw FrameTime card—not the sampled FPS card—so they describe frame delivery rather than a small set of periodic FPS readings.

Sampling and timing

Hardware and FPS / latency CSV files use the logging interval selected in AMD Adrenalin, usually between 250 ms and 5 seconds. Select the i beside Loaded files to see each detected interval.

When a sub-second interval is selected, FPS and Average Frame Time may still update only about once per second, so repeated values are normal. A raw FrameTime spike can appear before the next sampled FPS update. The reader keeps the recorded timestamps and does not shift either series to make them line up.

Use CSV values for broad trends and sustained conditions. Use FrameTime for individual hitches and consistency.

Loading session files

Load at most one Hardware CSV, one FPS / latency CSV, and one FrameTime file from the same session. Loading another file of the same type replaces the current one.

The reader checks names, time overlap, and recording duration. If it flags a possible first-sample outlier, you can exclude that reading without changing the source file and restore it from the Loaded files information panel.

Logs are normally stored in C:\Users\YOUR-WINDOWS-USERNAME\AppData\Local\AMD\CN. All processing happens locally in your browser.
